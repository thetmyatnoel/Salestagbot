## Missing

- Item-side view for user point 2: 'which customer bought THIS product' is only answered from the customer side. The item card for a SOLD unique piece (and 'recent') should show the buyer, paid, owed and method from the last live SALE group of that item, with a button to the customer card.
- A real 'deploy what is in the repo' step: the hourly menu matches the old 3600 s build, so the first action is to confirm the deployed version and republish dist/Code.gs as a new version of the same deployment, before any new feature.
- Reconciled Ledger column list: one LEDGER_COLS with Method (U) and Category (V) appended, one pay_methods setting, one set of PM buttons, used by sales, returns, payments, deposits, expenses, order deposits, delivery payments and refunds.
- Deposit earmarking in the data model (RefGroupID = order id on DEPOSIT rows) and in depositsFor/depositsHeldMap, plus Deposits view columns for 'earmarked to' so the sister can see which advance belongs to which voucher.
- Phase 0 additions: T6 Google sign-in from the shop (for the Sheet on a PC), T7 script.google.com + script.googleusercontent.com reachability and Telegram in-app browser open/save, T8 20 real measurement sheets through Gemini, T9 five voice notes with 'KBZ'/'Wave' inside Burmese, T10 confirm measurement field semantics with the tailor.
- Per-shop letterhead settings (brand, address, phones) for voucher, receipt and measurement PDFs; the two shops have different brands (Thiri Khit, Won Yone).
- Order status rollback on undo (generic U handler hook) and the >30-minute correction procedure for a delivered order in the runbook.
- Customer matching by phone before name, and a 'which customer?' chooser instead of silent substring auto-merge, now that phones and order history hang off CustomerID.
- A collapsing rule for rewrite triplets in dayReport/customer statement (one event, one printed line), or the decision to keep new-GroupID rewrites instead.
- Tests for: sales count with a Qty-0 row, Customers tab Phone surviving refreshViews, legacy blank Method not double-counted on the Dashboard, per-shop voucher numbering under concurrent creation, '7/3/20' measurement value round trip, ?start=V-xxxx routing, undo of delivery resetting status.
- Burmese review of ~100 new Messages keys (Design A ~40, Design B ~60) before the pilot; both designs assume the sister rewrites them but neither budgets her time on the critical path.

## Verdict

Research: correct mechanism (both primary sources verified: telegram-bot-api accepts only 2xx and has no redirect handling; Google documents the ContentService 302) and the right user check, but stale against the repo: durable dedupe and drop_pending_updates already exist in dist/Code.gs, and the 60-minute fingerprint shows an older build is deployed. Execute it now in this order: webhookStatus(), change ok() to HtmlService, rebundle, new version of the same deployment, probeWebhookResponse() must print 200, registerWebhook(), re-check pending_update_count = 0. Do not add a second dedupe. Design A (customers, payment method, expenses, PC): ready to build after the fixes above, in particular net-not-gross drawer line, no retroactive receipt renumbering, the Dashboard blank-Method double count, phone-first customer matching, and a decision on rewriteGroup-same-GroupID vs the existing new-GroupID pattern (either is fine, not both); 6 days is credible. Design B (tailoring): the data model and ledger mapping are sound in principle and fit the revenue-on-delivery rule, but it is not ready to build as written: deposit earmarking is not enforced by the lookups (an order's advance can be eaten by an unrelated credit sale), the kept-deposit cancellation corrupts the sales count, voucher numbering must be per shop and lock-safe, deep links do not route to orders, and it defines a second, conflicting payment-method model and adds a tap to the existing deposit/payment flows. Fix those, build parts 1-3 (orders, card, delivery) with chat/photo measurement capture first, and promote the HtmlService form to the first button only after the script.google.com reachability and in-app-browser test passes from the shop. Build order: deploy fix -> Design A -> Design B parts 1-4 -> form (after T7) -> photo path (after T8).
