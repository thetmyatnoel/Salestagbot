### C. The sync protocol: how a group's txs are validated (field by field)
- `syncValidateTx` requires: txId and groupId non-empty strings; `type` a key of `CFG.TX`; `shop` in `CFG.SHOP_IDS`; `time` parseable; `day` matching `^\d{4}-\d{2}-\d{2}$`; qty, amount, cash integers within `SYNC.MAX_QTY` (100,000) and `SYNC.MAX_AMOUNT` (100,000,000); unitPrice and costAtSale blank or a number; then exactly twelve optional fields (itemId, customerId, refGroupId, note, source, transcript, staffId, updateId, reversesTxId, method, category, receiptNo) each undefined, null, string or number, with no length limit; SALE/RESTOCK/RETURN/transfer rows need an itemId. **There is no whitelist and no "unknown field" rule: a tx carrying `dueDay` (or anything else) passes an old server untouched.** [apps-script/core_sync.js:369-388, :381-385; :52-53]
- `syncValidateBatch` (structural only): a `group` needs a non-empty `txs` array of at most `PUSH_MAX_ROWS`, every tx valid, `staffId` equal to the device's, every itemId existing, the group in the device's shop scope, one groupId; a `list` entry is checked by `syncListRecReason` only when the store has `addListOption` (else `bad_kind`); kinds outside `SYNC.ENTRY_KINDS` are `bad_kind`. [apps-script/core_sync.js:394-438, :404-416, :425-426, :75]
- `syncApplyPush` applies entries in `ENTRY_KINDS` order (customer 1, item 2, list 3, group 4, measurement 5, notice 6, error 7), quarantines a failing entry with its reason, marks `kindKnown` on a `bad_kind` the server does know, and refreshes the views once per batch when rows were accepted. [apps-script/core_sync.js:642-679, :652-662, :848]
- The phone side keeps an entry answered `retry`, or `bad_kind` without `kindKnown` for list/measurement kinds (an older server); a quarantined list entry clears `cursor.settingsHash` so the next pull replaces lists_json. [apps-script/core_sync.js:1382-1415, :1389, :1407-1410]
- Day checksums hash only `n`, `amount` and `cash` per day and shop, so a new column can never make a phone and the server disagree and trigger a repair loop. [apps-script/core_sync.js:876-903]
- Consequences for DueDay: an old phone (no dueDay) is accepted by the new server as before; a new phone pushing to an old server is accepted and the value is silently dropped because `gasSyncLedgerValues` maps only known columns (never a quarantine); a new server pulling to an old phone: `appendSynced` stores the extra key harmlessly. The gate `Settings app_min_version` can refuse too-old phones if the spec wants. [apps-script/gas_sync.js:160-170; app/app_store.js:444-452; apps-script/core_sync.js:339-340]
- The OVERPAID check and the shadow ledger read rows as given (`syncShadowPorts` over `rows`), so a PAYMENT row written at commit time after its SALE row in `txs` is fine (today's split shape). [apps-script/core_sync.js:593-606; apps-script/core_ledger.js:1020-1051]

### L. The ES5 check and the invisible-character rule
- The ground rule: `apps-script/core_*.js` and `app/app_*.js` are ES5 only (no let/const, arrows, classes, template literals, defaults, spread, destructuring, for-of, `Object.assign`, `Math.imul`, `Array.prototype.includes/find`, `String.prototype.includes/startsWith/padStart/repeat`); every app file header says "Plain ES5: var and function only". No file in the repo records the `npx acorn@8 --ecma5 <file>` command (grep over .md/.js/.json/.html/.txt/.cmd/.ps1/.sh finds no 'acorn' or 'ecma'); the only automated parses are `vm.Script` in build_app.js and run_gas.js, which accept modern syntax. So the acorn run is the orchestrator's convention, applied per core_*.js and app_*.js file; it checks syntax only (core_sync.js:136 already calls `Object.assign`, which no parser catches). ## CONSTRAINTS
- Columns are positional on write: both Ledger writers map `CFG.LEDGER_COLS` to cells by index, so the Sheet's header order must equal CFG order; the only safe place for `DueDay` is after `ReceiptNo`, and `ensureColumns` puts it exactly there. [apps-script/gas_store.js:385; apps-script/gas_sync.js:180; apps-script/gas_setup.js:257-265]
- Ledger has 26 columns and a new tab has 26: the 27th header needs `gasEnsureWidth` first (fresh and existing sheets), and the fake refuses the write otherwise. [apps-script/gas_setup.js:118-125; poc/fake_gas.js:194, :297-298, :408-411]
- A new row field must be added in six places or it is lost somewhere: `newTx` (exists on rows), `rewriteRows` replacement (survives credit conversion, method change, split), `gasStore.appendLedger` + `gasStore.ledgerRows` + `gasSyncLedgerValues` (Sheet), `textColumn` in setupSheet (stays text like Day). Sim and phone stores need nothing. [A above]
- Adding a key to `newTx` turns run_lists.js:703 red (26-key rule); adding a field to `listNormRow` or `listRowToCompact` turns run_lists.js:592/:869/:1003 and run_gas.js:1094-1098 red; adding a Lists column turns run_gas.js:443 and :460-461 red. D9 says existing checks are not edited except those the spec names, so the spec must name these or choose shapes that keep them (for example a Kind that lives only in the Lists tab and the compact rows is impossible without touching :592). [I above]
- A list field typed on a phone reaches the server only through `syncListRecReason` + `syncApplyListEntry` + `listUpsert` + `gasListValues`; today each drops unknown fields. [E above]
- Settings: a key missing from the Sheet reads as the code default; phones get the Sheet's value only after `setupSheet` (or a hand-typed row) and a pull; the app can override per device with `setting:<key>`. [F above]
- The whole scenario suite and run_round4 commit on the card's `S|id|n` tap; the simulator page, the app dev page and every suite share `seedSimWorld`. If the code default is `steps` (D5), the only way the untouched run_scenario stays green is `world.settings.sale_flow = 'quick'` in `seedSimWorld`, which then also applies to run_round4, run_sync, run_app, run_lists, the simulator and the dev page unless each overrides. [F, I above]
- The 21:00 overdue rule, the Dashboard SUMIF and three reports all read `Credits.Days` / `c.days`; D4's "overdue = past DueDay, or past OVERDUE_DAYS when blank" needs a per-credit decision inside `openCredits` (or a derived column) so that the Sheet formula, the summary and the simulator's ⏰ agree. [D above]
- A `bad_kind`/`retry` answer keeps a list or measurement entry on the phone; a group entry has no such protection, but a group is never refused for an extra field. [C above]
- Build outputs (`apps-script/dist`, `poc/dist`, `app/dist`) are regenerated, never edited; no new file under apps-script/ (the five loaders list files by name: bundle_gas FILES, build_simulator FILES, build_app CORE_FIRST, run_gas via bundle_gas, run_scenario/round4/lists inline lists). [J, H above]

## GAPS the spec has to settle
- Between "publish server" and "run setupSheet", a Telegram sale would `appendRow` 27 values into a 26-column Ledger (both writers); the README order avoids it, but the spec should say whether `appendLedger` grows the grid itself or the README order is the guard. [apps-script/gas_store.js:385; apps-script/gas_sync.js:174-183]
- `listRowToCompact` has no free letter for Kind that reads naturally (`k` = key); any new letter changes `lists_json` for every phone (fine: hash changes) and breaks run_lists.js:592 and run_gas.js:1094-1098.
- D6's "a row without a Kind is treated as a wallet": the natural place is `listNormRow`'s default, which also changes the exact-shape checks above; alternatively a `kindOf(row)` helper that reads `row.kind || 'wallet'` leaves the row shape alone but then `listNormRow` must still carry the field from the store.
- `syncApplyListEntry` sets `note = 'device <id>'` when the phone sends none; a Kind typed on the phone needs the field named in `syncListRecReason` (allowed values) and copied in `syncApplyListEntry`, and `gasListsPersist` only persists `label`/`detail` sets, so a Kind can only be set at append time unless a third `set` field is added.
- Simulator v2 (D8) has no build precedent for a fake server inside poc/dist: build_simulator.js excludes core_sync/sim_sync/sim_phone and the app files, while app/dev/index.html already wires exactly that set with classic script tags; the spec should pick one of the two as the base and say whether build_simulator.js grows its FILES or the dev page becomes the simulator.
- No automated check exists for the ES5 rule or for invisible characters in sources; if the spec wants them enforced, that is a new check (a new suite may run acorn or scan the files), not an existing one.
