| high | sync policy / append-only | The Sync design rejects money rows server side (overpaid, deposit_exceeds_held, scope) and has the phone DELETE them from its local ledger. Example: 500,000 owed; phone A takes 300,000, phone B takes 300,000 offline; B's row is refused in full although 200,000 of it is real cash, so the drawer no longer matches any record. Android Chrome is fine (shared storage). | Enroll by a short typed code: the bot replies with a 6–8 character one-time code bound to the TelegramUserID (15 min TTL, 5 attempts); the card says install first, open from the icon, type the code. | high | transport reachability | Every data byte goes to script.google.com (measured 2 of 2 tests only) and its 302 target script.googleusercontent.com (never measured). CORS-via-text/plain is community-documented, not official. | medium | client design: secrets | The API is called with ?api=1&token=<shared secret> in the URL of a public bundle; it protects nothing (anyone with the HTML has it) and puts a secret in browser history and server logs. | medium | phone clock / Day key | The Sync design accepts rows with the phone's Time and Day and merely warns on skew > 600 s. A phone a day off puts sales in the wrong business day, so the 21:00 summary, receipts and the monthly report are wrong and 'rows are not rewritten'. dayKey() uses epoch + fixed 6:30 offset, so only clock accuracy matters, not the timezone setting. | Learn offset = serverTime − clientTime at every sync, persist it, and make ports.clock.now() return Date.now() + offset (so Day is right even offline); show the ⏰ warning when |offset| > 5 min. Server still records ReceivedAt. |
| medium | ledger window and compaction (Sync §1) | R1–R4 window rules plus a monthly opening-stock fold on the phone plus a nightly stockCheck hash are the most bug-prone part of the whole design, built for 200 events/day/shop. The plan's own sample day shows 13 and 6 pieces; realistic volume is 20–60 rows/day for both shops, i.e. 10–20k rows/year, under 5 MB JSON. | Version 1 mirrors the whole active-year Ledger (plus carried-forward opening rows after the yearly archive, as the Transition design describes). No window, no fold, no hash. Revisit only if the Ledger passes ~50k rows. |
| medium | first bootstrap size on 2G | A fresh phone pulls 10–15k rows × ~300 B as JSON = 3–5 MB; at 50 kbps that is 8–13 minutes with retries, during which the install call stalls. ## Missing

- A single reconciled spec: the three results disagree on receipt numbering, auth, cursor, customer ids, rejection policy, voice format and hosting order.
- Fix for the pre-existing undo bug (mirrors in a new group leave undone credit sales open), which every server-side check and the Credits view depend on.
- An owner-only void (force undo at any age) with buttons in Telegram and the app, carried by every conflict ping; without it cross-phone conflicts can only be fixed by hand edits in the Sheet.
- An iOS-correct enrollment flow (typed one-time code inside the installed app, because a home-screen web app has separate storage from Safari).
- Accept-and-flag policy for money rows and an explicit list of the only rejections (duplicates whose end state already holds, structural errors).
- Phase 0 measurements of script.googleusercontent.com (the 302 target of every data call), of the chosen hosting origin, of a real browser POST from the shop SIMs, and of real webm/mp4/wav files through Gemini.
- Transport B specified as a file (not a text packet) shared to the bot, with a handleDocument on the server that reuses the same applyPush, and a drill for it in the pilot.
- Server-corrected clock on the phone so Day is right offline, instead of warn-only.
- Visibility of the other shop's open credits and deposits on a staff phone (mirror both shops' ledgers; UI filter by shop as today).
- Per-day checksums in pulls plus a protected-Sheet rule so a hand edit or a lost row is detected and repaired, and a 'void and re-enter' path so the sister never needs to edit the Sheet.
- Bootstrap compression or a compact row format for the first sync over 2G, with a progress bar.
- Incremental stock map in the phone store and a TapMs measurement on the sellers' own phones (the 300 ms promise is not guaranteed by sim_ports' O(items × ledger) scans).
- Decision to pilot with exactly one selling phone per shop plus the owner's phone: it removes every same-shop race (double sale, double undo, over-payment) from version 1 and leaves only cross-shop transfers and item edits as conflicts.
- Rule that an enrolled Telegram user no longer gets sale buttons in Telegram (the bot answers with 'sell in the app'), and the laminated card line 'only the 📷 inside the app'.
- Transfer handled online or server-computed, because it is the only operation that writes a quantity read from stale stock.
- Durable-before-✅ rule (confirmation shown after the IndexedDB commit).
- Exhaustion behaviour of receipt blocks if the Sync design's scheme is kept; otherwise the owner's sign-off on per-device receipt letters.
- Service worker update applied silently on cold start when the outbox is empty, instead of a banner the seller must tap.
- Yearly archive design for phones (drop rows ≤ archiveSeq, add opening rows) so Seq cursors survive the archive.
- Dev harness: poc/sim_sync.js with a fake server over the same in-memory sheet, two phones, fake-indexeddb, the 22 scenarios listed by the Sync design, and a build check that the bundle contains no token patterns.

## Verdict

Yes, local-first on the phone is the right real fix, not a hot fix. The slowness is structural: an inline-button tap in Telegram cannot show its result until phone → Telegram → Apps Script → Telegram → phone completes over a flaky link, and no server caching removes that round trip (it would shave 2–4 s to maybe 1.5–3 s, never to instant). A Telegram Mini App is online-only and cannot keep storage or a service worker on iOS, so it fails the same test. The existing code is unusually well placed for this: core_*.js is platform-free, the simulator already runs processUpdate() against in-memory ports in a browser, the ledger is append-only with UUID TxIDs so merging is a set union, and the Sheet stays the single truth. The three designs converge on the right shape (PWA shell cached by a service worker, IndexedDB mirror, outbox pushed to a JSON branch of the same /exec, Seq-cursor pulls, Telegram kept for pushes, PDFs, summaries and fallback). It is NOT ready to build as written. Blocking before code: (1) fix the pre-existing undo-group bug, since every server-side money check inherits it; (2) write one reconciled spec, because the three results contradict each other on receipt numbers, auth, cursor, rejection policy and voice; (3) replace reject-and-delete with accept-and-flag plus an owner void, otherwise the design quietly violates its own append-only rule on the phone; (4) fix the iOS enrollment flow (separate storage of home-screen web apps); (5) measure script.googleusercontent.com, the hosting origin and a real browser POST from both shops before gas_sync.js exists, with Transport B through Telegram as the designed fallback. Simplify version 1 hard: whole-year ledger mirror instead of windows and folds, one selling phone per shop so same-shop races do not exist yet, voice stays in Telegram until the format test passes, Android first and iPhone after P2/P7/P10. With those fixes it is a sound plan a single maintainer can build and the family can adopt; without them the first cross-phone conflict or the first iPhone install will produce exactly the silent data loss the owner is trying to escape.

## Total effort

About 30 working days of maintainer time (range 26–36): 2 core fixes, 2 Phase 0, 1 spec, 5 server, 6 phone data layer and tests, 6 PWA shell, 4 pilot support, 3 iPhone/voice/shop 2 follow-through, plus about 1 day of the family's time for Phase 0, strings and enrollment. Calendar: 10–12 weeks working evenings from abroad (1–2 weeks Phase 0 waiting, 5–6 weeks build, 3 weeks pilot in shop 1, then shop 2). The three submitted estimates (20, 25 and about 15 plus 5 days) each omit part of the others' scope; combined and with the fixes above, 30 is realistic. Recurring cost stays zero; the only optional spend remains the Gemini paid tier already in the plan.
