# MAP appsheet
SalesTagBot: the phone app (PWA) and the laptop/Sheet side — what each can record and edit today, how master lists reach phones, the PC/measurement paths, and what a new list (bank accounts, expense categories) or a measurement form would take.

## CONSTRAINTS
- core_*.js and app_*.js are plain ES5 (var/function, no imports) because one bundle runs in Apps Script, Node, the simulator and the PWA (apps-script/core_config.js:2-6; app/app_ui.js:14; app/app_store.js:19; tools/build_app.js:6-10).
- Ledger is append-only: corrections are mirror + replacement rows in the SAME group (rewriteGroup) or reversing mirrors (undoGroup); receipt numbers never renumber; blank Method on old rows reads as CASH and setupSheet never rewrites existing rows (apps-script/core_ledger.js:1-19, 88-92, 366-396, 425-459, 1001-1006; apps-script/gas_setup.js:5-9).
- Telegram callback data is at most 64 bytes: PM|<36-char group>|<KEY> leaves 12 bytes for a method key (CFG.METHOD_KEY_MAX_BYTES); longer keys are dropped from the buttons; the 🏦 row is capped at MAX_BANK_BUTTONS = 4 (apps-script/core_config.js:96-98, 107; apps-script/core_ledger.js:100-118; apps-script/core_bot.js:281).
- Settings is Key/Value and Messages is Key/Text; both reach phones only as whole maps when their hash changes, at the phone's next sync trigger (launch, commit, online, foreground; no polling) (apps-script/gas_setup.js:18-19; apps-script/core_sync.js:738-756; app/app_sync.js:500-520).
- Selling must stay two taps: scan, ✅; the default method CASH exists so the sale stays two taps (docs/design-round-3/SPEC-offline-first.md:25; POS-PROJECT-PLAN.md:507; app/app_ui.js:5-9).
- The pull/bootstrap payload has a fixed field set (ledger, items, customers, settings, messages, checksums, repair; staff/owners/scope/receiptLetter on bootstrap); any new tab or list that is not a Settings key needs server fields, client apply code, a new IndexedDB store with an APP_DB_VERSION bump, and bootstrap page-0 handling (apps-script/core_sync.js:752-758, 795-813, 1142-1168; app/app_store.js:21-36, 126-134).
- Outbox kinds are fixed (customer, item, group, notice, error); an unknown kind is quarantined as BAD_KIND, so a phone cannot push a Settings/list change until a new kind is added on both sides (apps-script/core_sync.js:73, 393, 472-654).
- One Method per Ledger row; rewriteCheck needs exactly one live row and no attached PAYMENT ('locked'), so a split payment is two rows and freezes later method/customer rewrites of that group (apps-script/core_ledger.js:46, 95-98, 408-423).
- No onEdit trigger exists: hand edits to Items/Customers reach phones only through the once-a-day fullMasters pull; Settings/Messages edits reach them on the next sync via the hash (apps-script/gas_main.js:139-149; apps-script/core_sync.js:735-737; app/app_sync.js:239).
- In the app ordersEnabled is false (store port lacks the tailoring functions) and the AI port lacks readMeasurementSheet; appInputModeFor has no 'meas'/'order' states; so any in-app measurement work starts from zero on the data layer (apps-script/core_report.js:14-16; app/app_store.js:264-339; app/app_ports.js:144-149; app/app_ui.js:68-77).
- ports.sync.isEnrolled is not implemented on the Google side, so 'sell in the app' never triggers; the Telegram bot keeps selling for enrolled staff (apps-script/core_bot.js:2799-2801; apps-script/gas_sync.js:372-378).
- Every pushed row must carry the device's own staffId and be in its shop scope (owner: both shops); a laptop or iPad enrolled by the sister can only write her staff's rows (apps-script/core_sync.js:343-357, 401-404).
- Each enrollment is its own Devices row with its own receipt letter and series; iOS home-screen apps and each browser origin keep separate storage, so a laptop browser or iPad is a separate device; SPEC v1 assumes one selling phone per shop (apps-script/core_sync.js:284-299; app/README.md:194-195; docs/design-round-3/SPEC-offline-first.md:44).
- Nothing in app/ may load from a third-party CDN or contain secrets; the build refuses a bundle with a bot token, AIza key or secret strings; config.js is public (app/README.md:8, 37-40, 237-248).
- The app's first deployment and the Phase 0 gates (P1 hosting origin, P3 browser POST to /exec from both shops' SIMs) are not yet done; no app publish is recorded in tools/publish-log.jsonl (POS-PROJECT-PLAN.md:759; app/README.md:172-181; docs/design-round-3/SPEC-offline-first.md:93-106).
- The Dashboard's expense-by-category block is generated at setupSheet time; a category added in Settings needs setupSheet re-run from the editor to appear there (apps-script/gas_setup.js:76, 273-281).
- HtmlService pages cannot host a PWA and would add script.google.com + the googleusercontent iframe to what the family's phones must reach (T7 untested); they are online-only with a 2-5 s cold start (docs/design-round-3/client-app.md:83; docs/design-round-2/critique.md:26; docs/design-round-2/design-A-customers-payments-expenses.md:140).
- Myanmar reachability first, no VPN, zero recurring cost; Telegram and Google front ends are the measured-reachable set (POS-PROJECT-PLAN.md:369-385; docs/design-round-3/client-app.md:27).

## OPTIONS
### Bank accounts as pay_methods keys + Messages labels (Settings only, no code)
HOW: The laptop user appends short ASCII keys to Settings pay_methods (e.g. CASH,KBZ,WAVE,AYA,CB) and adds Messages rows method_AYA = 'AYA · 123-456 ဦးမောင်'; optional Settings keys like account_AYA for the number/holder shown on receipts. payMethods() picks them up on the next request; phones get them at the next sync through settingsHash; the 🏦 row under sales, payments, deposits, expenses and deliveries renders them automatically in Telegram and the app (apps-script/core_ledger.js:105-118; core_bot.js:272-282, 1402-1404, 2367-2368; core_sync.js:738-756; app/app_store.js:401-405).
PROS: Zero schema or sync change; works on the live bot today and is backward compatible with existing Method values; editable from the Sheet on a laptop; tested paths (run_scenario 686-692, 757-770).
CONS: Keys limited to 12 ASCII bytes; only the first 4 non-cash methods are shown (MAX_BANK_BUTTONS = 4, out.slice(0,4)); no structured account fields (bank, number, holder, shop) without inventing more Settings keys; no dropdown or validation in the Sheet (errors only logged); no in-app 'add account'.

### Accounts as a new master tab synced like Customers
HOW: CFG.ACCOUNT_COLS (AccountID/Key, Bank, Number, Holder, Shop, Active, Rev, UpdatedAt) + gasTable reader and gasStampRev on edits; add accounts with Rev filtering to syncBuildPull/syncBootstrap and an ACCOUNT_PULL_FIELDS list; new IndexedDB store + APP_DB_VERSION 2 + upsertAccount in app_store.local; methodButtons reads active accounts (key still ≤12 bytes for PM|) and the Sheet shows the list as a grid the sister edits (apps-script/core_sync.js:70-72, 735-758, 801-813, 1145-1146; app/app_store.js:23-36, 379-390; apps-script/gas_store.js:77-92).
PROS: Rich rows (number, holder, per-shop), readable on receipts and reports; grid editing on the laptop; a natural dropdown source in the app.
CONS: Code on both sides (config, gas_store, core_sync, app_store, app_ui, tests) and a phone DB migration; hand edits still reach phones only on the daily full master pull unless an onEdit trigger or a bot/app edit path bumps Rev; still bound by the 64-byte callback and the 4-button cap unless the method row becomes a sub-screen.

### Expense categories stay a Settings string; add an in-flow '➕ new category' that pushes a new 'setting' outbox kind
HOW: At the end of the EC| grid add one ✏️ button -> await_text 'exp_cat' -> the typed Burmese label becomes key c_<4 hex from uuid> + label, appended to the local settings map (setSettings) and selected at once; the phone pushes {kind:'setting', key:'expense_categories', add:'c_ab12:label'} (new SYNC.ENTRY_KINDS value, validate + apply under the lock with a union merge by key, server writes the Settings cell; gasStore gains setSetting); other phones receive it via settingsHash; the laptop user can still rename labels in the Sheet (apps-script/core_bot.js:1345-1354; core_ledger.js:161-178; core_sync.js:73, 384-424, 490-507; gas_store.js:365-366 pattern).
PROS: Least clicks: the new option is created where it is needed, offline, and selected immediately (same pattern as ✏️ နာမည်အသစ် for customers); no new tab, no DB version bump; Telegram gets the same button with one typed round trip.
CONS: New entry kind on both sides plus merge rules for concurrent edits (two phones adding at once); keys must be ASCII so labels and keys diverge (Messages cat_<key> or the key:label string carries the label); the Dashboard block needs setupSheet re-run; an owner-approval step is not modelled.

### Generic 'pick or add' screen pattern for every list (method, category, customer, design, fabric)
HOW: Every list screen ends with one ✏️ 'new' button -> one typed/spoken value -> exact match reused, look-alikes offered with 'create this name', otherwise created locally and selected (matchCustomers/pickCustomer precedent); in the app the typed step is the existing text input bar; lists that are Settings-backed need option 3's sync kind, customers already sync (apps-script/core_bot.js:986-998; core_ledger.js:765-769; app/app_ui.js:602-619, 73-74).
PROS: Two extra taps only when a new option is needed; proven in tests 40/60; offline for customers today; same words in Telegram and the app.
CONS: Each list needs its own validation (ASCII keys, 12-byte limit for methods, 'other' always present for categories); Telegram's typed step costs a round trip; no dedupe across phones until the next sync.

### Measurement form inside the PWA (phone, laptop, iPad), not HtmlService
