# MAP botux
SalesTagBot Telegram bot: today's tap-by-tap UX for every money/order flow, the per-user state machine, how typed/voice input feeds the same flows, the keyboard builders (afterSaleKeyboard / moneyKeyboard / replyKeyboard / methodButtons), PC/Telegram Desktop entry, and an inventory of every pick-list with its data source and whether an "add new" path exists today.

## FACTS
- [Entry] A QR scan is a Telegram deep link: handleMessage treats '/start <payload>' as a scan. Payload matching isOrderId (V1-2532) opens the order card; payload matching /^[A-Z0-9_-]{1,64}$/ opens the item card via openTag; no payload shows the menu. The simulator's sim.start(user, payload) sends exactly '/start <payload>'.

## CONSTRAINTS
- Shared core files (core_*.js) are ES5 and run unchanged in Apps Script, Node tests, the browser simulator and the PWA; any new pick-list logic must live there and use only ports (core_config.js:1-7; core_bot.js:4-16; app/app_i18n.js:9).
- Telegram callback_data ≤ 64 bytes: PM|<36-char group id>|<KEY> leaves 24 bytes, hence CFG.METHOD_KEY_MAX_BYTES = 12 and keys must be short ASCII; labels go to Messages method_<KEY> (core_config.js:96-98; core_ledger.js:100-118; gas_setup.js:45-49).
- Only CFG.MAX_BANK_BUTTONS = 4 non-cash methods fit the 🏦 row under a sale/payment/deposit (methodButtons slice), and expense/delivery/refund rows show payMethods.slice(0,5) (core_bot.js:281,1402,2367,2420); a long bank list cannot be shown as one row today.
- Ledger.Method stores the KEY, not the label; reports and dayStats bucket by key (byMethod), so renaming a key breaks history while renaming a label is free (core_config.js:99-100,118; core_ledger.js:46; run_scenario.js:460-462).
- Selling must stay two taps: S|id|1 commits immediately as CASH (core_bot.js:366-373; core_ledger.js:230); any bank/account choice must remain a post-commit rewrite or an optional branch, never a question before the commit (design-A:43-47).
- A method or customer change is a rewrite that is only allowed while the group has exactly one live row, on the same day, and before any PAYMENT references it (rewriteCheck 'complex'/'expired'/'locked', core_ledger.js:405-423); a partial-payment design that writes a second money row into the sale group makes the sale's method button row disappear (afterSaleKeyboard shows methodButtons only when rewriteCheck.ok, core_bot.js:258-268).
- Gemini's INTENT_SCHEMA.method is a fixed enum of CASH/KBZ/WAVE/BANK (core_ai_prompt.js:81) and the prompt rules name only those four (44-46); a bank/account key added through Settings is invisible to voice until the schema/prompt are built from pay_methods.
- Every money row carries ONE Method and ONE Cash value (newTx core_ledger.js:23-55); a sale paid part cash / part bank must be modelled as several rows (e.g. SALE with cash part + PAYMENT with bank part, as deliverOrder already does inside one group, core_orders.js:285-320) because the ledger is append-only and existing rows/readers must keep working (production version 3).
- Per-user state is a single cached JSON (st:<uid>, 30 min TTL); multi-step flows must survive a stale tap by answering 'expired' and writing nothing (core_bot.js:1672-1677; run_scenario.js:725-732), and every committing callback must be registered in MUTATING_ACTIONS for the 120 s double-tap guard (core_bot.js:338-355).
- Settings tab is Key/Value and Messages tab is Key/Text; both reach the phone only through the hash-change pull (core_sync.js:738-756,1151-1152; app_store.js:322-326), and ports.store has no setSetting/setMessage/addDesign today (core_bot.js:4-16; gas_store.js:465-474), so an in-bot '➕ add option' needs a new write port in gas_store.js, the sim store and the app store, plus sync of that write from the phone.
- Customer pickers show only the 4 most recent customers of the staff's shop (recentCustomers(ports, staff.shop, 4)); the pay list is capped at 8, designs at 6, look-alike choosers at 4 (core_bot.js:1009,1146,1217,1260,1865,2499; core_config.js:51; core_ledger.js:994).
- The fabric picker encodes the list INDEX in the callback (OF|id|<i>), so reordering Settings fabric_presets between the screen and the tap changes the meaning of a stale button (core_bot.js:2111,2120).
- Expense categories must keep a lowercase ASCII key (stored in Ledger.Category) and 'other' is always present; the emoji map is code-only (core_ledger.js:161-178; core_config.js:101-103; core_bot.js:1348).
- Receipt numbers are never renumbered and rewrites keep the GroupID; a split-payment or extra-row design must not change the SALE row's receipt number (core_ledger.js:455,1005-1029; run_scenario.js:463,712).
- Owners pick the shop on expenses (ES|) while staff never do; any new list screen must respect staff.role/staff.shop scoping as the existing screens do (core_bot.js:1334-1343,1070,1214,1805).
- Voice intents feed open states by transcript (names, notes, values) and by firstNumber for number waits; a new flow step must declare its 'awaiting' name in buildAiContext and be handled in handleIntent's state section or it will be swallowed by the intent switch (core_bot.js:525-540,662-716).

## OPTIONS
### Bank accounts as pay_methods keys (zero code)
HOW: Add each bank/account as a short ASCII key in Settings pay_methods (e.g. CASH,KBZ,WAVE,AYA,CB) and a Messages row method_<KEY> with the Burmese label; the 🏦 row, expense/delivery/refund method rows, reports and the phone app pick it up on the next sync.
PROS: Works today with no code change (core_ledger.js:105-118; README H apps-script/README.md:141-145); labels can include the account holder or last digits.
CONS: Keys ≤12 bytes; only 4 🏦 buttons under a sale and 5 on expense/delivery rows (extra keys silently fall off the row, core_bot.js:281,1402); voice cannot return the new key (core_ai_prompt.js:81); no in-bot registration, the sister edits the Sheet on the laptop.

### BankAccounts list behind pay_methods with an in-bot ➕ (owner)
HOW: Keep Ledger.Method = key. Either keep the list in Settings (pay_methods + method_<KEY> labels so the existing hash-sync carries it) or add a BankAccounts tab (Key, Label, Bank, AccountNo, Active, Order) read by payMethods()/methodLabel(); add a store.setSetting (or addBankAccount) port in gas_store.js, poc sim store and app_store.js; add an owner-only '➕ ဘဏ်အသစ်' button at the end of the method rows → typed label → generated key (slug/next number) → write → redraw the same screen with the new key already applied (one extra tap).
PROS: Matches the user's 'add the option at the point of need' ask; keeps every existing reader untouched because the stored value is still a key; the 🏦 row rebuild (replyKeyboard/methodButtons) needs no change.
CONS: Needs new write ports in three stores and a sync path for a Settings write made on the phone; must raise or paginate MAX_BANK_BUTTONS (a second 🏦 row or a '🏦 …' submenu) once more than 4 banks exist; INTENT_SCHEMA.method must become a free string validated against payMethods() or an enum built from it.

### Split payment: cash part + bank part in one sale group
HOW: On the after-sale card add '💵+🏦' (e.g. PX|<group>) → ask the cash part with presets [half, other, 0] → rewriteGroup({cash: cashPart, method: CASH}) → ask the bank for the remainder (payMethods buttons) → commitPayment({groupId, amount: rest, method, note 'split'}) in the same flow; reply with pay_done-style text listing both parts. The group then reads: SALE (cash part) + PAYMENT (bank part), owed 0, exactly the shape deliverOrder already writes.
PROS: Uses only existing row types and readers (saleGroupInfo sums payments; openCredits sees owed 0; per-method buckets correct); receipt number unchanged; two or three taps after the sale.
CONS: Once the PAYMENT is attached rewriteCheck says 'locked', so the method buttons vanish and a mistake must go through undo of the payment then of the sale; receipt_total and card_buyer show one {method} and need a per-row breakdown; voice has a single method/paid pair (INTENT_SCHEMA) so a spoken split needs a second pass or two notes; the PWA's afterSaleKeyboard is the same code so it follows automatically.

### Expense categories editable from the category grid
HOW: Append '➕ အမျိုးအစားအသစ်' (owner, or anyone if the family prefers) as the last button of expenseCatScreen → typed label (text or voice) → key = 'c' + next number or a transliterated slug → store.setSetting('expense_categories', list + ',key:label') → re-send the amount screen for the new category (so the expense continues with no extra navigation); optional emoji default '📦'.
PROS: Least-click: adding the option costs one tap plus typing and lands the user exactly where they were; labels stay renameable in the Sheet; Ledger.Category keeps a stable key; expensePresets fills from Settings defaults until history exists.
CONS: Requires the setSetting port and its sync; EC|<key> must stay short (keys are tiny, fine); the grid has no cap today but grows 3 per row, so a dozen categories becomes a tall keyboard; voice mapping only needs the label (free-string category), so no schema change.

### Generic '➕ add' pattern for every editable list
HOW: One helper in core_bot.js: listScreen(kind) renders the current options + '➕ အသစ်' + '✏️ အခြား' + cancel; '➕' sets {kind:'await_text', purpose:'add_<kind>', resume:<state>} → typed label → kind-specific writer (Settings key for methods/categories/fabrics/due presets, Designs tab row for designs with BasePrice asked next, Customers via existing addCustomer) → the saved option is applied immediately and the interrupted flow resumes from `resume`. Mirror the same helper in the PWA (same core) and keep the Sheet tabs as the laptop editor for bulk edits.
PROS: One mental model for the family ('the last button adds one'); laptop users keep the Sheet; the phone users never leave the flow; designs get the missing add path (today only lookup, core_bot.js:1975-1987).
CONS: Each writer needs gas_store + sim + app_store implementations and a sync path for master-data writes from the phone (Designs rows would need Rev/UpdatedAt like Items/Customers to pull); Telegram keyboards cannot scroll, so lists over ~12 options need paging ('▶️ နောက်ထပ်' as OL does); the index-based OF| callback should switch to a key-based one before fabrics become editable in-flow.

### Laptop-first list maintenance, phone-first selling (surface split)
HOW: Keep selling, method marking and expenses on the phone bot/PWA as today; route list maintenance (banks, categories, designs with photos, measure fields, fabrics) to the laptop through the Google Sheet tabs that already feed every pick-list (Settings, Messages, Designs, MeasureFields), plus the typed-tag entry in Telegram Desktop for the occasional PC sale; add a one-line 'ℹ️ ဆိုင်ရှင်က စာရင်းထဲ ထည့်ပေးပါ' hint under lists instead of a ➕.
PROS: Zero core code; matches Plan 13.5 and design-A 3b ('the Sheet is the PC view; Settings and Messages are hers to edit'); measurements on an iPad/laptop already work through Telegram Desktop/web since every flow is buttons + typing.
CONS: Does not satisfy the user's point 4 (add an option at the moment it is needed on the phone); a new bank or category typed into the Sheet reaches the phones only at the next sync; the measurement web form (design-B primary, laptop-friendly numeric keypad) remains unbuilt, so a 32-field entry on a laptop is still a 32-message chat or a photo.
