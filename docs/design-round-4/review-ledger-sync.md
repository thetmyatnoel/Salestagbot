## [2] BLOCKER @ 8 and 9.1 (apply inside the batch lock), 1.5 (gasStore.addListOption under the script lock)
PROBLEM: syncApplyPush applies the whole batch inside sp.lock.run, which is the script lock on the real server. The spec makes the two new kinds call store.addListOption (specified 'under the script lock, the nextOrderNo pattern') and store.addMeasurement (already takes and releases the script lock) from inside that batch lock. No code nests the lock today. LockService keeps no hold count: a second waitLock on a held lock has no effect and releaseLock releases. So the inner finally frees the batch's lock. Because `list` sorts before `group`, every Ledger group of a batch that also carries a new account is then appended unlocked (LEDGER_SEQ read-modify-write, getLastRow()+1 then setValues), racing a Telegram sale or another phone: duplicate Seq or an overwritten Ledger row. If a runtime instead blocked the second waitLock, the batch would throw after 15 s, answer `busy` on every retry, and that phone's sales would never sync. The simulator cannot show either (its locks are no-ops), and step 3 may only touch `listAllMeasurements` in gas_store.js.
EVIDENCE: apps-script/core_sync.js:490-647 (whole apply inside sp.lock.run), :502-505 (kind order). apps-script/gas_sync.js:285-291 (script lock, release in finally), :173-180 (appendRows writes at getLastRow()+1), :96 (nextSeq read-modify-write), :246-254 (the only in-batch store write today bypasses gasStore.addCustomer's lock), :384-387 (Transport B uses the same apply). apps-script/gas_store.js:422-455 (addMeasurement: getScriptLock, waitLock, releaseLock in finally), :351-373 (the pattern prescribed for addListOption). apps-script/gas_main.js:75-81. No-op locks: poc/sim_sync.js:154, poc/sim_ports.js:309. Lock reference (https://developers.google.com/apps-script/reference/lock/lock): tryLock/waitLock 'has no effect if the lock has already been acquired'; releaseLock has no count.
FIX: Add to 1.5 (Google glue, step 2) and reference it from 8 and 9.1: 'One re-entrant script lock. gas_store.js defines `var GAS_LOCK_DEPTH = 0; function gasWithLock(fn, waitMs) { if (GAS_LOCK_DEPTH > 0) return fn(); var lock = LockService.getScriptLock(); lock.waitLock(waitMs || 15000); GAS_LOCK_DEPTH++; try { return fn(); } finally { GAS_LOCK_DEPTH--; lock.releaseLock(); } }`. Every holder of the script lock goes through it and nothing else calls LockService: `buildPorts().lock.run` (gas_main.js), `gasSyncServerPorts().lock.run` (gas_sync.js), `gasStore.addCustomer`, `nextOrderNo`, `addMeasurement`, the new `addListOption`, and `gasDedupe.remember` (5000 ms). Only the outermost call acquires and releases, so a store method called from inside a sync batch keeps the batch locked.' Add to 12 (run_gas.js): 'poc/fake_gas.js models LockService without a hold count (waitLock on a held lock returns at once, releaseLock releases). A `sync` call whose batch holds a `list` entry, a `group` entry and a `measurement` entry acquires the lock once and releases it once, after the last Ledger row is written.' 13 step 3 keeps gas_store.js limited to `listAllMeasurements` because the lock change is done in step 2.
