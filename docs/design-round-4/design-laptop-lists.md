# DESIGN laptop-lists
EMPHASIS: LAPTOP-FIRST LIST MANAGEMENT AND ONE CONSISTENT MODEL: every option list (bank accounts, expense categories, fabrics; designs and measure fields already) is a Sheet row with Key / Label / Active / Order that the computer-literate sister edits on the laptop; the bot shows the Label and stores the Key; phones receive list changes through the existing hash-sync; the phone's rare 'add new' writes a row into the SAME list and the laptop stays the place to rename, reorder, merge and retire. The split payment reuses the ledger shape that deliverOrder already writes, so no reader, report, formula or sync rule changes.

## SUMMARY
1. One new Sheet tab, Lists, holds every option the buttons offer: bank accounts (list pay_method), expense categories (expense_category) and fabrics (fabric), one row each: List, Key, Label, Active, Order, Shop, Detail, Note. Designs and MeasureFields keep their own tabs but follow the same Key / Label / Active / Order shape.
2. The sister registers or changes an option by typing one row on the laptop; dropdowns, a validated short Key, an Active checkbox and red highlights for duplicates make mistakes hard. Nothing is deployed: the bot reads the tab on its next request and every phone gets the new rows at its next sync.
3. A bank account is a Lists row: Key AYA, Label 'AYA ဦးမောင်', Detail = account number and holder. The 🏦 row under a sale, payment, deposit, expense, delivery or refund IS the dropdown: one tap per account, up to 6 without an extra tap, then a 'more' picker. The Ledger keeps storing the short key in Method, so old rows and reports are untouched.
4. Part cash, part bank: after Sold, tap '💵🏦 ခွဲပေး', give the bank amount (half or typed), tap the account. The sale row keeps the cash part, a PAYMENT row in the same group carries the bank part. Receipt says 'ငွေသား 10,000 · KBZPay 20,000'; drawer and bank totals, undo, credits and receipt numbers all work as today because this is the shape custom-order deliveries already use.
5. Expense categories come from the same Lists tab (label, emoji, order); the expense flow stays category, amount, method.
6. Every pick-list screen ends with '➕ အသစ် ထည့်': one typed or spoken name adds the option to the same list and the flow continues with it selected (expense moves on to the amount; the sale is marked with the new account; the fabric is set on the line). Anyone may add categories and fabrics; only owners add bank accounts.
7. Laptop: the Sheet for all lists and views, Telegram Desktop or the app in Chrome for typed-tag sales, the app in Chrome for measurements. No PC console is built.
8. Measurement book: one form screen in the phone app, the same bundle on an Android phone, the laptop's Chrome and an iPad home-screen app; fields come from the MeasureFields tab, values are typed or tabbed through, one Save writes the Measurements row through sync. Telegram keeps the photo and one-by-one chat paths.
9. Reports: the 21:00 line keeps 'ငွေသား · ဘဏ် · အကြွေး' and adds a per-account line when more than one account moved; the month PDF's by-method table lists each account; receipts with a balance print 'ငွေလွှဲရန်' with the shop's account details.
10. About 12 maintainer days: Lists tab + accounts + add pattern 3, split 1, sync kinds and app store 2, measurement form 4, tests and Burmese review 2. Deploy the server before the phones.

## ADD-NEW-OPTION PATTERN
One button, one question, same list. Every pick-list screen (account rows under a sale/payment/deposit/expense/delivery/refund, the expense category grid, the fabric row, the design screen, and the customer pickers that already have it) ends with the same two buttons: [➕ အသစ် ထည့်] (btn_add_option) and [✖️ မလုပ်တော့]. Tapping ➕ sets one state {kind:'await_text', purpose:'add_<list>', resume:{action, ...the ids the interrupted screen needs}} and edits the same message to '✏️ အမည် ရိုက်ပါ (ဥပမာ …)'; the answer may be typed (the app's text bar, appInputModeFor app/app_ui.js:68-77) or spoken (handleIntent takes the transcript for await_text states, core_bot.js:663-686; buildAiContext names the purpose as awaiting, :523-540) and is read before number parsing (handleText :556-572). The core then (1) normName-matches the text against every existing label of that list, active or not, and reuses the match; (2) otherwise derives a key with listKeyFor(list, label, existingKeys): ASCII letters/digits of the label, uppercase for pay_method and at most 12 bytes, lowercase for the others; a label with no ASCII gets a prefix + next number (M01, c10, f4); (3) calls ports.store.addListOption(rec) — Lists row on the server under the script lock, local row + outbox {kind:'list'} on the phone, world.lists in the simulator — with Active TRUE, Order last, Shop = the staff member's shop for pay_method, Note 'added by {staff} {day}'; (4) resumes the interrupted screen with the new option already applied: EC → the amount screen for that category; PM → changeMethod rewrite; EM → expenseMethod commit; ODM/OXM → deliverCommit/refund; SXM → the split commit; OF → the line's fabric set and the due screen; OI (designs, Telegram-only, owner) → a Designs row with DesignCode = the typed code and the price screen next, the sister fills name, photo and days on the laptop. Who sees ➕: everyone for expense categories, fabrics and customers; owners only for bank accounts and designs. The laptop is where lists are managed in bulk (rename Label, emoji in Detail, Order, Active, merge twins by retiring one); the phone add is the one-off exception and never edits or deletes. Index-based callbacks (fabric OF|id|<index>) become key-based so a stale button after a laptop reorder cannot pick the wrong option. New committing callbacks (SXM, and the add resumers that commit) join MUTATING_ACTIONS (core_bot.js:338-341).

## RISKS
- Deployment order matters: a phone on the new build pushing a list or measurement entry to the old server is quarantined as BAD_KIND and the row leaves the phone (core_sync.js:393; syncApplyPushResults :1120-1134). Deploy gas first, run setupSheet, raise app_min_version (core_sync.js:329-330), then publish the app; the app's first deployment and Phase 0 gates P1/P3 are themselves still pending (POS-PROJECT-PLAN.md:759).
- After a split the sale group has two live rows: no 👤 attach, no 💳 credit, no 🏦 re-mark, no note (rewriteCheck 'complex'/'locked', core_ledger.js:413, :417-420); the only corrections are ↩️ within 30 minutes (undo of both rows, CFG.UNDO_WINDOW_MIN core_config.js:9) or the owner's 🚫. Attach the customer before splitting when it matters.
- Keys are forever: a mistyped account or category added from a phone (or a Label typed into the Key column on the laptop) leaves rows with that key; validation on the Lists tab and the ASCII slug rule limit it, and an inactive row still labels old rows, but a merge of two twins is a laptop job (retire one; its old rows keep the old label). Two phones adding the same label offline get the same key or a numbered twin; the server remaps a clashing key and logs it.
- The legacy Settings keys and Messages method_* / cat_* rows stay as fallbacks, so for a while there are two places; editing the old place does nothing once the Lists tab has rows. README H and a header note on Settings say so; a later setupSheet can blank the three legacy values after the pilot.
- More than six active accounts for one shop cost an extra tap through the 🏦 နောက်ထပ်… picker, and long labels on 3-per-row Telegram buttons truncate on narrow phones; keep labels short (bank + holder's short name).
- Voice: Gemini only returns a method key that is in the schema enum; until the enum is built from payMethods (core_ai_prompt.js:81) a spoken new account is not recognised and the sale is recorded CASH; the 🏦 row then fixes it.
- Lists reach an idle phone only at its next sync trigger (no polling, app/app_sync.js:500-520); a seller may see the old grid for a few minutes after the sister's edit, and a category added on one phone is unknown to the other shop's phone until it syncs (the key still travels on the rows).
- The measurement form needs the laptop browser and the iPad enrolled as devices (each a Devices row with a receipt letter, core_sync.js:284-299) and desktop IndexedDB persistence depends on the persist() grant; order linking is by typed voucher number because orders are not in the app yet (ordersEnabled false, app/app_store.js:264-339); prefill from the last session needs the daily full-masters pull or bootstrap to have happened.
- The receipt's 'ငွေလွှဲရန်' line prints account numbers on something customers receive; the Detail column must hold only what the owner wants customers to see (a blank Detail prints nothing).
- Telegram inline keyboards reject the whole keyboard when any callback exceeds 64 bytes; SXM|<uuid>|<12-byte key>|<7-digit amount> is 61 bytes, so amounts above 9,999,999 or a 13-byte key would break it; the key limit is enforced by validation and the amount by MAX_AMOUNT; the scenario's byte check guards it (poc/run_scenario.js:1230-1231).
- The Dashboard QUERY blocks are formulas the owner can break by editing; writeDashboard always rewrites the tab on setupSheet (gas_setup.js:216), so a re-run restores them.
