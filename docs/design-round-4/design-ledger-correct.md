# DESIGN ledger-correct
EMPHASIS: LEDGER AND REPORT CORRECTNESS WITH THE SMALLEST CODE CHANGE. Every new fact is stored in rows and Settings values that today's readers already understand: a split sale is a replacement SALE row plus a PAYMENT row in the same group (the exact shape deliverOrder writes in production), a bank account is a short key in Settings pay_methods with its label in the same cell, and a new option is one appended token in a Settings cell. No new Ledger column, no new row type, no new tab, no new sync entry kind, no app DB change. The UX is built on top of that model with a post-commit button, as the 🏦 buttons are today, so the two-tap sale is untouched.

## SUMMARY
1. Selling stays two taps (scan, ✅). Everything about money methods happens on the card AFTER the sale, as the 🏦 buttons do now.
2. A buyer who pays part cash, part bank: tap 💵+🏦 ခွဲပေး on the sold card, tap the bank, tap "half" or type the bank amount. Done. The receipt says "ပေးပြီး 30,000 (ငွေသား 10,000 · KBZPay 20,000)", the drawer and the bank wallet each get their part, nothing shows as a credit.
3. Each bank account is one short code and a Burmese name in one cell of the Settings tab (pay_methods: CASH,KBZ:KBZPay,WAVE:WavePay,AYA:AYA ဦးမောင်). Every account becomes a 🏦 button under sales, payments, deposits, expenses and deliveries, on Telegram and in the phone app, with no Messages row to type any more.
4. Expense categories work the same way in the cell expense_categories (fabric:အထည်ဖိုး, ...). The expense screen already offers them as buttons.
5. When an option is missing at the moment of need, the last button of that list is ➕ (new bank / new category): type its name once, it is saved and used right away, and the entry continues where it was. If the name already exists it is reused, never duplicated.
6. Lists are registered on the laptop in the Google Sheet (bulk edits) or in Telegram Desktop with the same ➕ buttons; phones get the new list at their next sync.
7. The phone app sells and records expenses exactly like the bot; it cannot yet write to the Settings tab offline, so its ➕ records the entry under "other / ဘဏ်လွှဲ" with the typed name as the note and sends the owner a message to register the option (nothing is lost, and the money totals are still right).
8. Reports: the 21:00 line keeps "💵 drawer · 🏦 bank" net movement; the month PDF already prints one row per account (ဝင်/ထွက်/ကျန်); receipts and the customer card show both parts of a split.
9. Corrections keep working: ↩️ မှားသွားတယ် reverses the whole split sale within 30 minutes (then re-sell); the owner can void later. A split sale cannot be re-edited piecemeal, so attach the customer before splitting.
10. Measurements: use the existing Telegram chat or photo-of-the-paper-page flow on phone, laptop (Telegram Desktop) and iPad now; the in-app form comes after the app's first deployment. Voucher numbers need no change: custom orders already continue the paper book's number (Settings order_next_no_S1/S2), sales keep their receipt number, and the shop letterhead cells can stay blank.

## DATA MODEL
- Ledger: NO new column and NO new row type. A split sale appends three rows to the sale's own group: (1) mirror of the live SALE row (qty/amount/cash negated, Method and Category copied, ReversesTxID = original, Note 'rewrite', Source UNDO); (2) replacement SALE (Cash = original cash - bank part, Method unchanged (CASH), UnitPrice/Amount/CustomerID/ReceiptNo copied, Time/Day = the original's, Note 'split' when blank); (3) PAYMENT (Amount = Cash = bank part, Method = the account key, RefGroupID = the sale group, ItemID and CustomerID copied from the sale, Note 'split', Time now, Day today). Rows 1-2 are exactly what rewriteGroup writes today (apps-script/core_ledger.js:428-459); row 3 is exactly what commitPayment writes (:289-301 per map) except it lives in the sale's group, as deliverOrder's PAYMENT does (apps-script/core_orders.js:285-325 per map). ## RISKS
- After a split the group has two live rows: rewriteCheck returns 'complex'/'locked' (core_ledger.js:413-420), so 👤 attach, 💳 မကျေသေး, 🏦 re-mark and 📝 note disappear from that card; the only corrections are ↩️ within 30 minutes (then re-sell) or the owner's void. Mitigation: split_hint on the card and the rule 'attach the customer first, then split'; the split amount screen's 'အကုန်' path keeps a full-bank correction a one-row rewrite.
- Burmese button width: the method row now holds three buttons per row ('🏦 AYA ဦးမောင် 0123' can be long); Telegram wraps, the app's HTML buttons wrap; keep account labels short (the ask text gives an example). New strings need the family's Burmese review (POS-PROJECT-PLAN.md:563).
- Label-match reuse can over-match: a typed 'ဘဏ်' is contained in 'ဘဏ်လွှဲ' and reuses BANK; a typed 'ကား' matches 'ကားခ'. Acceptable for a family shop and safer than duplicates; the add_exists reply names what was reused so the seller can cancel and retype.
- Auto-generated keys (BK1, c3) are opaque in the Ledger tab and in the Dashboard's category block labels '(key)'; reports print labels, so this is cosmetic. Keys must never be renamed after use (history is keyed).
- Settings cell format: a comma or colon inside a label breaks the CSV; the ➕ flow strips them, the Sheet editor must avoid them (README rule). A label given in the token shadows a Messages method_<KEY> row for the same key (precedence rule); keep one place per account.
- Dashboard: the 'Expenses by category' block is generated at setupSheet time (gas_setup.js:273-281); a category added by ➕ or in the Sheet is in menus and PDFs at once but on the Dashboard only after setupSheet is re-run.
- Phone app v1 cannot write Settings: a ➕ on the PWA records the row under 'other' / BANK with the name as the Note and pings the owner; the row's bucket stays generic forever (append-only) unless the owner voids and re-enters it. If the family adds options from the app often, the v2 'setting' outbox kind is the fix (~60 lines, both sides).
- More than 6 non-cash accounts: the 7th and later fall off the buttons silently (slice), as the 5th does today; raise MAX_BANK_BUTTONS further or page the row if that ever happens.
- Voice: Gemini's method enum is fixed to CASH/KBZ/WAVE/BANK (core_ai_prompt.js:81), so a spoken 'AYA နဲ့' is not recorded as AYA until the optional schema change; buttons are the primary path and the pilot keeps voice in Telegram only (SPEC-offline-first.md:72).
- Sync ordering: the split's rows must stay in the order mirror, replacement, PAYMENT inside the entry; otherwise the server's OVERPAID flag (a ping, never a rejection) can fire (core_sync.js:604-608). writeGroup preserves array order (core_ledger.js:58-66) and the collector keeps append order (app/app_store.js:541-547).
- Concurrent list edits: server writes are under the script lock (gas_store setSetting), so two sellers adding at once both land; a phone that has not synced yet shows the old list until its next trigger (no polling, app/app_sync.js per map). A laptop edit and a bot ➕ at the same moment can collide on the Sheet only if the sister is mid-edit in the cell; last write wins.
- Receipt gaps: an undone split leaves the sale's ReceiptNo as a gap, as every undo does (core_ledger.js:1001-1006); unchanged policy, worth repeating to the owner.
- The day PDF prints the bank part of a split as a separate 'ငွေလက်ခံ' line under the sale; the owner may read it as a credit payment at first. The sale line's ငွေလက်ခံ column (10,000) and the (ပြင်) mark make it consistent; a Note column value 'split' is printed on both rows (core_report.js:154).
