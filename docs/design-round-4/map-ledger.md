# MAP ledger
SalesTagBot money model: how SALE/PAYMENT/DEPOSIT/EXPENSE rows store money and method, how reports split drawer vs bank, where the pay-method and expense-category lists live, and how one sale paid partly cash and partly bank (10,000 CASH + 20,000 KBZ) can be represented with the fewest changes.

## FACTS
- Ledger column semantics: Amount = value of the event (SALE +, RETURN -, EXPENSE -, PAYMENT +, DEPOSIT +); Cash = money that actually moved on THIS row (SALE: paid now; PAYMENT/DEPOSIT: all; DEPOSIT_APPLIED: 0; EXPENSE: negative); Method = how the cash moved (CASH, KBZ, WAVE, BANK); a sale's open balance = Amount - Cash - its DEPOSIT_APPLIED rows - PAYMENT rows that reference it. Column order is TxID, GroupID, Time, Day, Shop, ItemID, Type, Qty, UnitPrice, Amount, Cash, CostAtSale, CustomerID, RefGroupID, Note, Source, Transcript, StaffID, UpdateID, ReversesTxID, Method, Category, Seq, ReceivedAt, DeviceID, ReceiptNo.

## CONSTRAINTS
- Shared core files are ES5 and run unchanged in Apps Script, Node, the simulator and the PWA; any new flow is core code, not app code (apps-script/core_config.js:1-7; app/app_ui.js:6-9, :13-14).
- The ledger is append-only: no row is edited; corrections are mirror + replacement in the same group (rewriteGroup) or mirrors (undo); the sync server quarantines a mirror whose target is in another group (apps-script/core_ledger.js:2-3, :14-18; apps-script/core_sync.js:576-584).
- Rewrites are possible only for a group with exactly one live row of a rewritable type, on the same day, with no live PAYMENT referencing it; any multi-row money group (split sale, delivery with deposit) loses the 👤/credit/🏦/note buttons and can only be undone (apps-script/core_ledger.js:408-423; apps-script/core_bot.js:258-268).
- Telegram callback data is at most 64 bytes and the keyboard is rejected as a whole otherwise; method keys are therefore at most 12 UTF-8 bytes (PM|<uuid>|KEY = 40 + key) and any new split callback must fit the same budget (apps-script/core_config.js:96-98; apps-script/core_ledger.js:100-118, :134-149).
- Receipt numbers are never renumbered: on the phone one ReceiptNo is stamped per SALE row, so a sale group must keep exactly one SALE row or it consumes extra numbers (app/app_store.js:275-292; apps-script/core_ledger.js:1001-1029; docs/design-round-3/SPEC-offline-first.md:71).
- Selling stays two taps with CASH as the default; any split or method choice must be an optional extra tap after the sale, as today's 🏦 buttons are (POS-PROJECT-PLAN.md:507; apps-script/core_bot.js:199-213, :253-270).
- Backward compatibility with the live bot (version 3) and existing rows: readers treat blank Method as CASH and blank Category as other; a new row TYPE is rejected by syncValidateTx on any server that does not know it, whereas new rows of existing types (SALE + PAYMENT) are accepted and read correctly by old code (apps-script/core_ledger.js:88-92; apps-script/gas_setup.js:5-9, :273-281; apps-script/core_sync.js:359-362, :329-330).
- Every row with Cash != 0 is counted into by-method totals and the Dashboard's Cash SUMIFS regardless of type, so a representation must not duplicate cash across rows (apps-script/core_ledger.js:784-825, :844-847; apps-script/gas_setup.js:227-236).
- The sync protocol can carry only customer, item, group, notice and error entries from a phone; Settings and Messages are pulled read-only, so adding a bank account or an expense category must happen on the Sheet or through a server-side (Telegram/online) flow (apps-script/core_sync.js:73, :738-758; app/app_store.js:401-410).
- OVERPAID flagging on the server evaluates a PAYMENT against the shadow ledger including earlier rows of the same group, so within a split group the SALE row must precede the PAYMENT row in txs (apps-script/core_sync.js:587-608, :616).
- At most 4 🏦 buttons are shown under a reply and 5 method buttons on the expense/delivery method screens (apps-script/core_config.js:107; apps-script/core_bot.js:281, :1402, :2367).
- The undo window is 30 minutes from the first live row; after that only the owner's void reverses a group (apps-script/core_config.js:9; apps-script/core_ledger.js:378-379, :399-401).

## OPTIONS
### (a) SALE row with Cash = cash part + a PAYMENT row (method KBZ, RefGroupID = sale group) written in the SAME group at commit time
HOW: Extend commitSale (apps-script/core_ledger.js:221-234) with an optional bank tender {method, amount}: SALE row cash = total - bank, method CASH; second newTx {groupId: saleTx.groupId, type: PAYMENT, refGroupId: saleTx.groupId, itemId, customerId, amount: bank, cash: bank, method: methodFor(key, bank), note: 'split'}; one writeGroup([saleTx, payTx]) so the phone emits one outbox group and the server writes one atomic group. UI in core_bot: an extra button while rewriteCheck passes (e.g. '💵+🏦'), ask the bank amount with presets/other via an await_number purpose like 'credit_paid' (core_bot.js:1133-1141), then the method row like deliverPaid (core_bot.js:2367-2375); for an already-committed cash sale do rewriteGroup({cash: cashPart}) then append the PAYMENT into the same group. Add Messages strings and MUTATING_ACTIONS keys.
PROS: Zero changes in core_sync, core_report, core_config, gas_store, the Dashboard and the app: saleGroupInfo already subtracts PAYMENT rows that reference the group (owed 0), openCredits skips it, addMethodCash splits drawer 10,000 / bank 20,000, groupMethods + receiptMethodText already print 'ငွေသား 10,000 · KBZPay 20,000', undoGroup reverses both rows with same-group mirrors, receiptNumber and the app's per-SALE ReceiptNo see one SALE row, customer totals add both parts, old servers accept both row types and old rows are untouched. It is the exact shape deliverOrder already uses in production (core_orders.js:285-325; scenario 69-70).
CONS: The group has two live rows, so rewriteCheck says 'complex'/'locked': no 👤 attach, no 'not fully paid', no 🏦 re-mark and no note after a split; corrections are undo + re-sale within 30 minutes or owner void. The day report shows the bank part as a separate ငွေလက်ခံ (PAYMENT) line rather than inside the sale line; statsWhere.payments (unused) includes split parts; afterWrite rewrites the Credits/Deposits/Customers views on every split sale made through the bot.

### (b) SALE row with Cash = total plus a new SPLIT/TENDER row type per method
HOW: Add CFG.TX.TENDER; either keep SALE Cash = total Method CASH and write signed TENDER rows (CASH -20,000, KBZ +20,000), or write SALE Cash 0 and TENDER rows carrying all the cash; add TX_LABEL, a statsWhere case, and new handling in saleGroupInfo, openCredits, customerSummaryMap, groupMethods, afterWrite, the Dashboard formulas and syncValidateTx vocabulary.
PROS: Keeps the sale's own line as the single money line in some reports; models a tender as its own concept.
CONS: Most code changes of the three: a new type is quarantined as MALFORMED by any server that does not know it (core_sync.js:362), which breaks phone-before-server deployment; addCash/addMethodCash count every cash row so the signed-transfer variant inflates gross cashOut/drawerOut and the Dashboard's Cash>0 SUMIFS, and the Cash-0 variant breaks owed/Credits/customer totals until six core_ledger functions plus core_report and the Dashboard are taught the new type; the group still has several live rows so the rewrite limits are the same as (a).

### (c) Two SALE rows in one group (10,000 CASH and 20,000 KBZ)
HOW: Call newTx twice from a new commit: one SALE qty -1 amount 10,000 cash 10,000 CASH and one SALE qty 0 amount 20,000 cash 20,000 KBZ (amount set directly since commitSale derives amount from qty), one writeGroup.
PROS: No reader changes: saleGroupInfo sums all SALE rows (owed 0), openCredits skips it in the pre-pass without computing info, groupMethods and the receipt method text work, undo and the sync server accept it, by-method totals are right.
CONS: Breaks the one-SALE-row-per-sale assumptions: the app stamps a second ReceiptNo on the second SALE row (gap in the gap-free per-phone series) while receiptNumber returns the first; receipts print 'name × 0 · 20,000'; the day report and the Sheet show two sales; lastLiveSale returns the qty-0 row; a qty-0 SALE with a positive amount is a new semantic every reader, formula and future import must tolerate; rewrite limits identical to (a). Worst option.

### Accounts as Settings rows keyed by the method key (recommended shape for 'register which bank account')
HOW: Keep Ledger.Method = the short key listed in Settings pay_methods (<= 12 bytes, e.g. KBZ, AYA, CBPAY) and the label in Messages method_<KEY>; add Settings rows acct_<KEY> = 'bank|owner|number|note' (or JSON) and a helper accountInfo(ports, key) in core_ledger; receipts, vouchers, expense/deposit replies and the owner's reports can print the account detail; the dropdown in the app is the existing 🏦 button row (raise MAX_BANK_BUTTONS or add a second row if more than four accounts).
PROS: No change to payMethods, methodLabel, rows, callbacks, sync (Settings already reach every phone whole by hash) or the app; old rows keep reading; adding an account is two Sheet rows (Settings + Messages) or one bot/laptop flow that appends them.
CONS: Account details are only as structured as the encoding of one Settings value; adding from the phone is impossible without a new sync entry kind or a server-side flow; the Messages label row is a second place to edit unless the label is also derived from acct_<KEY>.

### Accounts tab (new master tab) with full columns
HOW: New tab Accounts (Key, Label, Bank, Owner, Number, Active, Note) with gasStore.listAccounts, CFG.ACCOUNT_COLS, a pull/bootstrap field in syncBuildPull/syncBootstrap, an app store and sim port, and payMethods/methodLabel reading it before Settings/Messages.
PROS: Clean structure for the owner on the laptop; labels and details in one row; Active flag retires an account without touching history.
CONS: Touches core_config, gas_store, gas_setup, core_sync (pull, bootstrap, hashes), app_store, sim ports and tests; the rows still store only the key; much more work than Settings rows for the same user-visible result.

### 'Add a new option while entering' (new category or account mid-flow)
HOW: For expense categories: in the EC grid add a '➕' button that asks for a label (await_text), then on the SERVER path appends 'key:label' to Settings expense_categories (a new gasStore.setSetting) and commits the expense; on the phone path the flow would have to queue a new outbox entry kind (e.g. 'setting') that syncApplyPush applies, or fall back to writing the entry with category 'other' and the typed label in the note (expenseCategoryKey already keeps unknown words in the note, core_bot.js:736-739) for the owner to promote later on the laptop.
PROS: Least-click for the seller; the note fallback needs no protocol change and nothing is lost.
CONS: A true in-flow addition from the phone needs a new sync entry kind plus a setSetting port on the server and sim (core_sync.js:73, :384-419, :507-646), and a key derivation rule (ASCII key <= 12 bytes for methods); category keys are free-form ASCII but a duplicate label must map to the existing key.
